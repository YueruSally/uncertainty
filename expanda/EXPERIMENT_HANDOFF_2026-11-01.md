1. 统一了组件比较框架：相同实例、算法种子、冻结 CCP 情景、q90 目标、

   3.39%，未通过准入门槛；该结果只能证明技术链路可以运行，不能作为学习
   已成功的正式结论。
6. 建立了 I/M 的最终正式流水线：20 个全新实例、5 个算法种子、Base/I/M
   三种方法、pop=250、gen=200、每次 50,250 次真实评价，共 300 次优化运行，
   最后对固定 Pareto 前沿做每实例 5,000 个独立情景的 OOS 评价。

## 5. 明天的 C 计划

### 5.1 先检查 I/M

确认正式流水线是否运行、五个 shard 的完成数和 ETA；不根据中途结果修改
冻结的 I/M 科学配置。

### 5.2 C 小范围筛选

不再做逐切点强制替换。新 C 同时重新设计：

1. 父代配对：选择 Pareto 位置互补、路径结构具有可组合性的父代；
2. 子代生成：每次 crossover event 最多做一次联合 splice；
3. 子代选择：用 cost、emission、time、delay、reliability 的 balanced 结构
   分数选择可行子代；
4. 保持同一 400 次真实评价预算，不使用免费反事实目标评价。

小实验固定为 10 个开发实例 × 3 个种子 ×（Base + 两个预注册 C 变体）
= 90 次，pop=20、budget=400、200 个冻结 CCP q90 情景。预计 15--30 分钟。

### 5.3 C 正式实验

小实验只用于在两个预注册 C 变体中选择一个。选定后冻结规则，在 I/M 正式
实验完全相同的 20 个实例、5 个种子和情景上运行 100 个 C 任务，直接复用
已有 100 个 Base 任务，不重复 Base。预计 4--7 小时（10 并行进程），随后
使用相同 5,000 个 OOS 情景统一比较 I/C/M。

## 6. 组件选择原则

最终只在完全相同的 20×5 配对块上比较 Base、I、C、M。主要汇报指标为：

- 相对 Base 的平均 OOS HV 提升；
- 平均优化运行时间。

根据正式结果选择平均 OOS HV 提升最高且没有实现/预算违规的组件，再进入
Transformer/PPO 学习阶段。规则结果是 teacher/strong prior，不等于学习结果。
